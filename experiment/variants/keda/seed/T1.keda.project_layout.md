# Project layout — environment and boundaries (KEDA treatment)

How this service is deployed, the runtime architecture you author into, and
what is yours to change. Read together with `docs/keda.md` (the stack
reference — the **mandatory** approach for this project's runtime
provisioning).

You have **no live access to the cluster** — you cannot `kubectl apply`,
inspect, or run anything against it. This document is the architecture, and CI
feedback is your ground truth. You **can** validate manifests offline (no
cluster needed) with `kubeconform <file.yaml>`, which checks them against the
Kubernetes and KEDA schemas — use it before finishing.

## Runtime architecture

```
  host                                  kind cluster (namespace: ecb)
  ┌───────────────────────┐             ┌───────────────────────────────────┐
  │ photoshare service    │  reads      │  your metric path ──► KEDA         │
  │  (uvicorn, port 8080) │◄────────────│    (reads APP_HOST:8080/metrics)   │
  │  reads CACHE_HOST/PORT │             │                                   │
  │  reads DB_DSN          │             │  KEDA ScaledObject ──► scales      │
  └──────────┬────────────┘             │    the redis Deployment 0↔1        │
             │ port-forward             │                                   │
             │ svc/redis ──────────────►│  redis (Deployment + Service)      │
  ┌──────────┴────────────┐             │    KEDA + metrics-server: installed│
  │ Postgres (capped)     │             └───────────────────────────────────┘
  │  given; DB_DSN injected│
  └───────────────────────┘
```

- The **app runs on the host** as a local `uvicorn` process. Anything in the
  cluster that reads it must target the host address — write the host as
  `APP_HOST` wherever it appears (e.g. `http://APP_HOST:8080/metrics`) and
  the bring-up rewrites every `APP_HOST` to the cluster-reachable host IP.
- The **cluster is given**: a `kind` cluster, namespace `ecb`, with
  **KEDA** and **metrics-server** already installed. A `redis:7-alpine` image
  is pre-loaded.
- The **transactional store** is a capped Postgres, given; the app reads
  `$DB_DSN`. Not yours to provision.

## Bring-up (owned by the platform; runs outside this repo)

- Deploy applies every `k8s/*.yaml` in this repo to the `ecb` namespace,
  then port-forwards your Redis Service to the app's `CACHE_HOST:CACHE_PORT`,
  then starts the service on the host with `DB_DSN`, `CACHE_HOST`,
  `CACHE_PORT`, `SERVICE_PORT`, `TASK` set.
- Teardown removes what deploy created and scales everything back down.
- Every verification starts from a clean world: it runs on a throwaway
  cluster provisioned for that verification alone, so nothing you or the
  autoscaler created during a previous verification survives into the next.
- You do not author or edit the bring-up.

## What you author, and where

- **`k8s/`** — the cache-scaling stack: the Redis cache (Deployment + Service),
  the metric pipeline the autoscaler reads, and the KEDA autoscaler itself.
  The Redis **Service must be named `redis`** (the bring-up port-forwards
  `svc/redis`). Every name/key that appears in more than one file — the Redis
  Service name ↔ the autoscaler `scaleTargetRef` ↔ the scrape target ↔ the
  metric name the trigger reads — must agree.
- **`app/`** — discovery only: route hot reads through the cache when it is
  reachable at `CACHE_HOST:CACHE_PORT` (an answered round-trip, not client
  construction), fall back to Postgres when it is not. No app-side
  provisioning or scaling calls, no application-side provisioning SDK.

## Boundaries

- The cache 0↔1 happens **out-of-process**, driven by the load signals the app
  exports — never from app code.
- The store is fixed and platform-owned; you do not declare it.
