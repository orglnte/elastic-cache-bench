# Project layout — environment and boundaries (Pulumi treatment)

How this service is deployed, the runtime architecture you author against, and
what is yours to change. Read together with `docs/pulumi.md` (the Automation
API reference — the **mandatory** approach for this project's runtime
provisioning).

You have **live access to the project's Docker endpoint**: `DOCKER_HOST` in
your environment points at it (the same endpoint your provisioning code will
use at runtime). You can run/inspect containers there and exercise your
provisioning code against it before submitting. `python3`, the `pulumi` and
`pulumi_docker` packages are installed. The store and the deployed service
are NOT running during authoring — the review deploys and load-tests your
build; CI feedback remains the verdict.

## Runtime architecture

```
  host
  ┌────────────────────────────┐          ┌──────────────────────────────┐
  │ photoshare service         │ Pulumi   │ project Docker endpoint       │
  │  (uvicorn, port 8080)      │ Automation│  $PULUMI_DOCKER_HOST          │
  │  your provisioning code    │ API      │  (isolated; provisioned       │
  │  reads DB_DSN              │ up/destroy│   resources live here)        │
  └──────────┬─────────────────┘          └──────────────┬───────────────┘
             │                                            │ stack.up()
  ┌──────────┴────────────┐                    ┌──────────┴───────────┐
  │ Postgres (capped)     │                    │ redis (container)    │
  │  given; DB_DSN injected│                    │  appears on up()     │
  └───────────────────────┘                    │  gone on destroy()   │
                                               └──────────────────────┘
```

- The **app runs on the host** as a local `uvicorn` process. Your provisioning
  code, running inside it, drives the cache lifecycle by executing Pulumi
  programs (Automation API) against the project Docker endpoint
  `$PULUMI_DOCKER_HOST`.
- The cache the app consumes is reachable at
  `$PULUMI_CACHE_HOST:$PULUMI_CACHE_PORT` **once your program has published
  the container's `6379`** (see `docs/pulumi.md`); before `up()` and after
  `destroy()` no cache answers there — the port mapping may still accept a
  TCP connection and then close it empty, so judge cache liveness by a real
  reply (e.g. redis `PING`), never by connect success.
- The **transactional store** is a capped Postgres, given; the app reads
  `$DB_DSN`. Not yours to provision or release.

## Bring-up (owned by the platform; runs outside this repo)

- Deploy starts this service from the project venv with `DB_DSN`,
  `SERVICE_PORT`, `TASK`, `PULUMI_DOCKER_HOST`, `PULUMI_CACHE_HOST`,
  `PULUMI_CACHE_PORT`, `PULUMI_BACKEND_URL`, `PULUMI_CONFIG_PASSPHRASE` set
  for the service process.
- Teardown stops the service and removes the provisioning substrate wholesale
  — but **within a run**, releasing what you provisioned is your code's job;
  nothing reconciles or garbage-collects between spikes.
- Every verification starts from a clean world: the provisioning substrate
  and the Pulumi state backend (`PULUMI_BACKEND_URL`) are emptied after each
  verification, so nothing your program provisioned, and no state describing
  it, survives into the next one.
- You do not author or edit the bring-up.

## What you author, and where

- **`app/`** — the runtime provisioning, in service code, via the Pulumi
  Automation API (see `docs/pulumi.md`): bring up the redis cache container
  under sustained saturation, destroy it on drain, expose the current cache
  client, and keep serving through mount, release, and fallback. Stack state,
  idempotent re-mount, orphan avoidance, and routing around a just-destroyed
  cache are all yours — there is no external system tracking any of it.

## Boundaries

- The provisioning **is** the code: no Kubernetes manifests, no external
  autoscaler configs, and no shelling out to `docker` — resource lifecycle
  goes through the Automation API.
- The store is fixed and platform-owned; you do not provision or release it.
- The Docker endpoint is the project's provisioning substrate, not a general
  playground: the cache container is the only resource this task needs.
