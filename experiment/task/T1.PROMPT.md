# TODO — add a dynamically provisioned cache

This repo holds a **working** photo-sharing service (FastAPI + Postgres; see
`README.md`). All endpoints serve, every read goes to Postgres, and the
service exports its load signals. There is no cache anywhere.

The hot read path is `GET /photos/search?q=...` — a CPU-heavy ranked query.
Under a read-load spike it saturates Postgres: the pool backs up and the
`pool_pressure` signal (exported at `GET /metrics`) climbs.

Traffic profile (from production observation): a baseline of a few tens of
rps. Two kinds of elevation occur: short blips that overshoot the store and
drain on their own within seconds, and genuine spikes that ramp up over tens
of seconds and stay, saturating it. Their order and count vary from day to
day.

## The task

Add support for a **dynamically provisioned read-through cache** to this
service. **The approach to follow is documented in `docs/` — it is
mandatory**; do not substitute a different provisioning mechanism.

1. Under **sustained** saturation of the hot read path, a cache backend
   (Redis / ephemeral KV) is brought up **at runtime** and hot reads start
   being served through it. Short blips that the store can absorb must NOT
   bring it up.
2. When the load **recedes**, the cache is released / scaled back to zero —
   not left running while idle. Reads then fall back to Postgres correctly.
3. This must work repeatedly: a later spike mounts the cache again.

How you structure the code (and any declarations the documented approach
calls for) is yours to decide.

**Aim to get it right in as few submissions as possible.** Each submission
runs an expensive CI verification; treat it as a costly, real deployment, not
a free retry. Reason the design through and validate offline (see
`docs/project.md`) *before* submitting — the goal is a correct build in the
fewest iterations, not trial-and-error.

## Contract (verification depends on these; do not break them)

- The served API is exactly the current endpoints, unchanged, on port `8080`.
- `GET /metrics` keeps exporting the load signals (`pool_pressure` at
  minimum).
- `GET /health` stays the liveness/readiness endpoint AND gains a field
  `cache_mounted`: `true` **only while a cache backend actually exists and
  answers**, `false` otherwise (including at idle, right after deploy).
- `TODO.md` and `docs/` are documentation — do not change them, or the
  project instructions become wrong and the project fails. The bring-up
  (deploy/teardown) is platform-owned and runs outside this repo — see
  `docs/project.md` for the runtime architecture and what is yours to change.
- The service must keep serving every request throughout: mount, spike,
  release, and after release (reads fall back to Postgres).

## Acceptance criteria

- [ ] `AC1` The cache is provisioned **conditionally, at runtime**, driven by
  the saturation signal — not unconditionally at startup, not always-on.
- [ ] `AC2` A release/scale-to-zero path exists and is driven by the drain
  signal; after it fires, hot reads fall back to Postgres correctly.
- [ ] `AC3` The lifecycle repeats: a later sustained spike mounts the cache
  again.
- [ ] `AC4` `cache_mounted` in `/health` is truthful (see Contract).
- [ ] `AC5` Every runtime resource named in one place is declared/used
  consistently everywhere it is referenced.
- [ ] `AC6` Verified end to end: e2e assertions pass and, under the load
  test, the scaling behavior above is observed while the service keeps
  serving. The load test runs the event sequence in several arrangements —
  the behavior must hold for all of them.

## Out of scope

Auth, image bytes/object storage, thumbnails, multi-AZ/region, the bootstrap
substrate.
